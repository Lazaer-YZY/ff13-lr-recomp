## 2026-11-07 — SDK Android build decisions (from the port agent, adopted)
- SDL3 is shared-only on Android (`SDL_SHARED ON`, `SDL_STATIC OFF`): `SDLActivity` does `System.loadLibrary("SDL3")` and needs SDL's exported `JNI_OnLoad`; desktop builds keep static SDL. The APK ships `libSDL3.so`, `librexruntime.so`, `librexgpu-xenos.so`, `libc++_shared.so`, `libmain.so`.
- The codegen CLI is not built for Android (`REXGLUE_BUILD_TOOLS=OFF`); codegen stays on the host. Consequence: the generated `rexglue.cmake` must tolerate a missing `rex::rexglue` target (template fix in progress).
- Android installs do not write the CMake user package registry, so host projects cannot accidentally `find_package` the Android prefix. Consumers pass `CMAKE_FIND_ROOT_PATH=C:/dev/rexglue-android` + `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE=BOTH`.
- Bionic gaps were fixed in the SDK, not worked around in the app: no `ucontext` (own aarch64 fiber switch: x19-x30, d8-d15, SP; FPCR not saved — revisit if guest fibers misbehave), no robust mutexes, no float `from_chars`, `jthread` behind `-fexperimental-library`.
- Thunk tables: when the boot loop reports consecutive fatals with a fixed stride, stop the loop, map the discovered run in `generated/` (grep `DEFINE_REX_FUNC(sub_<prefix>...)`), and seed the gaps in one codegen pass instead of one 8-minute iteration per entry.

## 2026-11-07 — Bulk discovery of pointer-only functions: structural thunk scan, not pointer scan
- Measured on the 40 addresses the harness found by trial: a data-pointer scan of the image (`tools/scan_pointers.py`) found **none** of them; every one was either inside a GAP_FILL function (gap-fill had merged a run of 8/16-byte thunks `addi r3,r3,-4; b target` / `lis; li; addi; b target` into one function) or in an unfilled hole right after a 16-byte DISCOVERED thunk.
- `tools/find_thunks.py` therefore walks holes and GAP_FILL bodies in the dumped image (`rexglue codegen --dump-image/--dump-functions`, SDK commit 093bd0e): a straight-line sequence ending in `b`/`blr`/`bctr` that starts after the previous terminator is a thunk; the code following a thunk run is a function regardless of length; branch targets from inside the region are labels and excluded. Recall 15/15 on the trial set, 2,403 candidates.
- Seeding policy: append all candidates as bare entries tagged `# thunk-scan`, run codegen, and let its validation reject the false positives (jump-table case blocks look like thunks but tail-jump to labels, which shows up as UnresolvedCall sites); `tools/prune_from_report.py` comments out the seeded entry containing each error site; repeat until clean. Cheaper and safer than guessing sizes.

## 2026-11-07 — Frame judder: the effect workers' spin waits; multi-object wait wakeups
- Found with new diagnostics (LR_BARRIER_LOG=1, thor_measure SCHEDSTAT=1, PROFILE + host symbolisation of the pulled perf data). The main thread's long waits are in a frame barrier (sub_82E0C480). Its gate is released 13-24 ms late by one of the four vfx-qix-effect workers. About 60% of those workers' CPU went to two guest spin primitives: sub_82C45EE0, a run-once election, and sub_82C45F58, an n-thread spin barrier. A worker spinning on a core starved the participant it waited for.
- Fix (lr_hooks.cpp): host replacements with the same atomics on the same guest words. They spin briefly, yield for up to 50 us, then sleep on a futex on the guest word, woken by the hooked writers (`LR_SPIN_BACKOFF=futex`, the default; `yield` and `0` remain for comparison). - Where the corridor's 25.0 ms of GPU time went (Turnip, 401 MHz, `--vulkan_gpu_timing` + `--vulkan_gpu_trace_frame`): every 1280x720 k_8_8_8_8 resolve (ten per frame, 1.81 ms) was already fed into its texture (SDK patches 62/68), so each one paid twice: the direct-resolve compute dump into guest memory that nothing on the GPU reads, plus the feed draw. - **Lazy resolve dumps (SDK patch 77, `vulkan_resolve_feed_lazy_dump`, default on):** a fed 1x k_8_8_8_8 resolve records a pending dump instead of dispatching it: the resolve's push constants, the fed texture and the swap flag. `SharedMemory::RequestRanges` got a listener hook (before uploads and allocation); the render target cache flushes pending dumps whose memory intersects any requested range (texture loads, vertex/index data, memexport) by running the same direct-resolve compute shader with the texture as the source - through a BGRA-swizzled view when the feed swapped red and blue, so the shader's own swap gives the exact bytes the eager dump would have written - and the resolve's own EDRAM base and pitch as the "render target" base, which makes the shader's source pixel equal the texture pixel (requires the texture fed at the resolve's EDRAM offsets and covering the whole resolve rectangle; other feeds stay eager). A later resolve covering a pending range drops it (12 per frame deferred, 12 dropped, 0 ever written in the field); a partial overlap flushes it first (the RequestRange of the new resolve's destination hits the hook). ## 2026-11-09 19:25 — Texture sign specialization built (SDK patch 89): -9.5% GPU work; async shader translation actually on
- **Design as planned (ours; idea from Xendroid+, not its code):** the translator gives each fetch constant a pixel shader samples a specialization constant (SpecId 1000 + fetch constant) holding a sign class (0 runtime = the system-constant word as before, 1 all unsigned, 2 gamma RGB + unsigned A, 3 all gamma), applied by selects that the driver folds. ## 2026-11-09 21:10 — Effect barrier (82E0C500): what it is; three wake-up/affinity fixes measured, none helps
- **Structure (generated-code analysis):** sub_82E0C480 is a counted gate, not a plain barrier. ## 2026-11-13 00:15 — Battle starts are the game's GPU heap compaction; memexport barriers coalesced (SDK 0108)
- **What the ~10,000 memexport draws are:**
  - The render job's heap compaction (`sub_82B528B8`) moves graphics resources through its copy callback at heap+32. That callback is `sub_82A842A0`.
  - `sub_82A842A0` saves and sets device state (`sub_82A841E8`: render target / depth calls `sub_829BA798`/`BA580`/`BA378`), then copies 32 MB-capped, 128-byte-aligned chunks on the GPU (`sub_82A83348` -> draws), then restores (`sub_82A826D0`).

  - The owner's session logged compaction calls of 0.87-0.93 s several times and 1.93 s once (23:20:41). The same fixes speed those up.
- **Barrier coalescing (SDK 0108, `vulkan_memexport_coalesce_barriers`, default on):**
  - `VulkanSharedMemory::Use(kGuestDrawReadWrite, range, coalesce)` skips the barrier between consecutive memexport draws when the new draw's vertex fetches don't overlap the pending written range. The ranges accumulate.
  - The next reader (any other usage, or an overlapping draw) gets one barrier covering all of them.
  - Index buffers from shared memory, compute reads, transfers, etc. are other usages and always barrier.
