# Reference notes (one page)

What the reference repos give us, what they don't, and what is unknown for Lightning Returns. File pointers are into `refs/`.

## 1. Lighthing-Recomp (FFXIII, same Crystal Tools engine) — what we reuse
- **Project shape.** A ReXGlue project is tiny: `ffxiii_manifest.toml` + `src/main.cpp` (`REX_DEFINE_APP(ffxiii, FfxiiiApp::Create)`) + `src/ffxiii_app.h` (a `rex::ReXApp` subclass with optional virtual hooks: `OnPreSetup`, `OnLoadXexImage`, `OnConfigurePaths`, ...) + a CMakeLists that includes `generated/rexglue.cmake` and calls `rexglue_setup_target`. Everything else is SDK. We copy this layout 1:1.
- **Manifest content is NOT reusable** (different game: Title ID 535107E4 vs our 5351081B), but its *character* is: 434 lines, almost entirely `[entrypoint.functions] 0xADDR = { size = 0x8..0x30 }` entries, i.e. tiny indirect-call thunks (`REX_CALL_INDIRECT_FUNC` / lone `blr`) the analyser could not find. One real split-loop fix (`0x8257CC98 = { size = 0x1F0 }`). Expect the same for LR: hundreds of small thunk entries, few hard cases.
- **Workflow we copy** (`tools/ffxloop.sh`): run game, grep log for the last `guest address 0x...` of an unresolved branch, append `0xADDR = { size = 0x10 }`, `rexglue codegen --force --ignore-stamp`, confirm the emitted `sub_ADDR` is a thunk, rebuild, repeat. We will script this for Windows + adb logcat.
- **SDK patch we must carry**: `patches/rexglue-sdk/0001-xenos-exp-adjust-from-fetch-constant-word-3.patch`. The SPIR-V translator read texture `exp_adjust` from fetch-constant dword 4 instead of dword 3, giving near-black textures. Game-agnostic Xenos bug; check whether v0.10.1 already contains it, else apply to our SDK branch.
- **Known Crystal Tools runtime quirks they hit**: XMA contexts created but never kicked (no music/SFX); a thread spinning on unknown XMA register 0x601; hair/minimap render-to-texture corruption; the function-dispatcher global critical-region lock must stay (bypassing it made objects vanish). Linux-only build (clang-20, Wayland env in run scripts). Expect LR to share the XMA and RTT issues.

## 2. ReXGlue SDK v0.10.1 — what exists, what Android needs
- **Toolchain**: clang/clang++ GNU driver (not MSVC/clang-cl), C++23, CMake >= 3.25, Ninja Multi-Config, 22 vendored submodules (fmt, spdlog, toml++, CLI11, inja, simde, xxHash, libmspack, FFmpeg fork for XMA, SDL3 static, imgui, tracy, o1heap, glslang/SPIRV-*, Vulkan headers). No vcpkg/FetchContent. Windows CI: `choco install llvm cmake ninja`, `cmake --preset win-amd64`, `cmake --build out/build/win-amd64 --target install`. Vulkan is OFF by default on Windows (D3D12 on); non-Windows is Vulkan-only.
- **CLI**: `rexglue init --project-name lr --xex-path <game_root>/default.xex --game-root <dir>` renders manifest/CMake/main.cpp templates; `rexglue codegen [manifest] [--ignore-stamp] [-f]` runs analysis + codegen (no separate analyse command). Analysis errors: UnresolvedCall, MissingJumpTable, JumpTargetOutOfBounds, DiscontinuousFunction, UnimplementedInsn; `-f` emits code anyway. Manifest schema (`src/codegen/config.cpp`): `[functions]` (size|end, name, parent), `[[switch_tables]]` (address of bctr, register, labels), `indirect_calls=[...]`, `[[invalid_instructions]]`, `[[midasm_hook]]`, `[analysis]` thresholds, `includes=[...]`. XEX decrypt (retail/devkit AES) + LZX + `.xexp` title-update patching live in the runtime's `xex_module.cpp`, which codegen links.
- **arm64 is real**: generated code uses `simde_mm_*` (NEON on aarch64), FPSCR has an FPCR path, the posix exception handler decodes arm64 faults, Linux-arm64 and mac-arm64 are built in CI. So the CPU side of Android is "free".
- **Android is half-ported Xenia residue.** Present: `REX_PLATFORM_ANDROID` macros, ASharedMemory/ashmem backing in `memory_posix.cpp`, `VK_USE_PLATFORM_ANDROID_KHR` + `instance_khr_android_surface.inc`, Android lib names in `dynlib.h`. Missing: nobody calls the Android init (`InitializeAndroidSystemForApplicationContext` undefined), `include/rex/ui/surface_android.h` does not exist but `vulkan_presenter.cpp` includes it, `window_sdl.cpp` has no `SDL_PROP_WINDOW_ANDROID_WINDOW_POINTER` branch, `src/ui/CMakeLists.txt` falls to `surface_gnulinux.cpp` (xcb/wayland), `thirdparty/CMakeLists.txt` forces SDL X11/Wayland/ALSA ON for any UNIX, `src/core` links `rt`, FFmpeg needs a Bionic config header, top-level CMake treats Android as Linux. All build/glue work, no redesign.
- **GPU path is favourable**: Vulkan loaded by `dlopen("libvulkan.so")` + `vkGetInstanceProcAddr` (no volk), so Turnip injection via libadrenotools is a ~10-line change in `vulkan_instance.cpp`. Shaders: Xenos microcode to SPIR-V in-process, no DXC. Hard device requirements: independentBlend, fragment/vertex stores-and-atomics, geometryShader, fillModeNonSolid (Adreno 740/Turnip: yes). Fragment-shader-interlock optional (falls back to the FBO render-target path). No BDA/int64 requirement found.
- **Memory**: 0x120000000-byte file-backed mapping, base probed at 1<<32 ... 1<<63 with MAP_FIXED_NOREPLACE; SIGSEGV/SIGILL handlers for MMIO + GPU write-watches. Same scheme Lost Odyssey proved on Android (fixed 0x1_0000_0000). Risk: Android's 39-bit VA and 16 KiB-page devices (not the Thor).
- **Runtime shape**: `rexruntime` SHARED + `rexgpu-xenos` SHARED (dlopen'd by name) + app exe; game target via `rexglue_setup_target` (generated macro) / `rexglue_configure_target`. On Android the app must become `libmain.so` loaded by SDL's `SDLActivity`, plugin in jniLibs.

## 3. Lost Odyssey Recomp — the Android layer we copy (it is XenonRecomp+plume, not ReXGlue)
- **Gradle project** `packaging/android/`: AGP 8.9.3, Gradle 8.11.1, compileSdk/targetSdk 35, minSdk 26, build-tools 35.0.0, **NDK 28.2.13676358**, JDK 17, abi arm64-v8a, `c++_shared`. Two modules: `:app` (diagnostic probe, Gradle externalNativeBuild, CMake 3.22.1) and `:runtime` (game; packages prebuilt .so from a separate CMake invocation with `android.toolchain.cmake -DANDROID_PLATFORM=android-26`, output `libmain.so` + `libSDL3.so` + `libc++_shared.so` + adrenotools hook libs; `useLegacyPackaging = true` so hooks are extracted). Signed with the debug key. Link flags `-Wl,-z,max-page-size=16384 -Wl,-Bsymbolic-functions`.
- **Java** (`runtime/src/main/java/io/github/freefrank/lostodyssey/`): `RuntimeActivity extends SDLActivity` (libs c++_shared, SDL3, main; env via SDL `nativeSetenv`; immersive mode; lifecycle publishes logs), `GpuDriverActivity/Catalog/Store` (downloads Turnip zips from GitHub releases, per-package dir under `files/gpu_driver/`, boot-pending flag drops a failing driver), `GameFolderActivity/GameStorage` (Android/data/<pkg>/files/game, SAF tree picker, ISO import via `--install`), `PlayerLogs` (LO_LOG_DIR = external files/logs, crash handler), `TouchControlsView` + layout/persistence (Java overlay sends a JNI `nativeSetTouchInput` snapshot, OR-ed with a real pad, hidden when a controller connects).
- **Native**: `gpu/video.cpp:172-244` `adrenotools_open_libvulkan(RTLD_NOW, ADRENOTOOLS_DRIVER_CUSTOM, nullptr, hookDir, driverDir, soname, ...)` then `dlsym vkGetInstanceProcAddr`; ICD mode for PanVK; retry with system driver on failure; `tu_dont_reserve_descriptor_set=true`. Lifecycle: SDL3 event *watcher* for WILL_ENTER_BACKGROUND triggers swapchain rebuild; audio watcher reopens the device after resume. Memory: `mmap(0x100000000, 4 GiB, MAP_FIXED_NOREPLACE)` + memfd views; E-view 4 KiB offset breaks on 16 KiB-page hosts (the probe reports it).
- **Pipeline proof caveat**: the full APK needs Lost Odyssey's `default.xex` for codegen (ppc/ is git-ignored and CMake fatal-errors without it). We build the `:app` probe APK instead; it exercises JDK/Gradle/AGP/SDK/NDK/CMake/adb and doubles as the Thor memory/Vulkan diagnostic.
- Docs to come back to: `packaging/android/README.md`, `docs/archive/notes/android-port-research-2026-10-02.md`, `docs/notes/pipeline-first-use-stalls.md`, `tools/patches/README.md`.

## 3b. lr-ffxiii-port (leftisthominid) — the existing port of THIS title (found 2026-11-07, primary reference)
- ReXGlue **v0.10.0** (c94f5eb) port of the same disc release (`default.xex` SHA-256 pinned in `builder/pipeline.ps1`), Windows + Android, GPL-3.0, LLM-assisted. Layout: `project/` (manifest.in with `ctr/xer/reserved/cr_as_local = true`, `analysis/*.toml` 11 files ~600 entries, `src/lr_hooks.cpp` 5,009 lines + app header/.inc menus/PS3+Steam save importers), `plugin/` (rebuilds `rexgpu-xenos` from 604 modified v0.10.0 graphics sources against the installed SDK: texture replacement and renderer fixes), `android/` (`rexglue-sdk-android.patch`, 29 files; `game/` libmain entry; `plugin/`; `project/`), `builder/` PowerShell pipeline, `converters/` (PS3/Steam assets).
- Overlap with our Android SDK work: it independently fixed surface_android, fiber, memory/threading, chrono/numeric shims, main_android. What we lacked: SDL audio driver changes, filesystem_posix, xam_content(+aggregate) saves, mmio_handler, xmemory, gpu_plugin_loader, input_system, window_sdl/windowed_app_context_sdl, SGSR 1 upscaler shader.
- Status per README: played on Windows; Android build had only run through on Linux at the time. Requires the disc release without title update (ours).

## 4. LR-specific and unknown
- Disc: USA XGD3, Title ID 5351081B, Media ID 4A99274C, XEX v0.0.0.8, imports only xboxkrnl.exe + xam.xex; static libs D3D9/XAUDIO2/XMP/XGRAPHC 21250 (Aug 2013 XDK). Data is `weiss_data/{sys,zone,movie}`: ~20 huge `white_*.x360.bin` archives + `filelist*.bin` (Crystal Tools "white" packfiles). No loose files, so the VFS just needs to serve big reads from the game root.
- **Known after codegen (2026-11-07)**: the analyser recovers **81,253 functions** and **29,314 indirect call sites**; only **25** tail-branch targets needed manifest entries (bare `0xADDR = {}`), no jump tables or discontinuous functions were reported. Output: 218 `lr_recomp.N.cpp` (232 MB, largest 1.4 MB), analysis ~270 s on the dev PC. The XEX decrypts and loads with the SDK's loader (Title ID/Media ID confirmed). Still unknown: whether a title update exists or matters (v0.0.0.8 base).
- Unknown until boot: XMA kick behaviour (FFXIII's bug may be engine-wide), render-to-texture correctness on the FBO (non-interlock) path, Turnip feature gaps (geometry shaders OK; check `shaderStorageImageExtendedFormats`, image atomics, `EXT_custom_border_color`), memory footprint (FFXIII desktop ~1.6 GB RSS; Thor has 12 GB), and whether the 4.5 GB fixed reservation lands on Android's 39-bit VA.
- Unknown until later phases: performance of simde-on-NEON generated code at 720p/1080p on 8 Gen 2 (Lost Odyssey reports 25-35 FPS on Adreno 840), battery/thermals, 60 FPS unlock feasibility (engine timing assumptions).

## 5. Prior art for performance on Android (researched 2026-11-07, full notes in the ignored `out/prior_art_perf.md`)
- **Lost Odyssey Recomp (Android):** keeps game threads off the little cores using `cpu_capacity` (`refs/LostOdysseyRecomp/LostOdysseyRecomp/os/host_scheduling.cpp:44-72,157-170`), the same idea as our `PinThreadsToFastCores`. It raises only its audio thread's priority (nice -16, `host_scheduling.cpp:181-184`) and logs per-thread schedstat (`LO_FRAME_STATS`). Its renderer uses a virtual 60 Hz vblank with FIFO present, and a late frame is shown at once rather than caught up (`gpu/frame_pacer.h`). Its ROADMAP judges the hot frame CPU/thermal-bound, not GPU-bound.
- **lr-ffxiii-port (Android):** its Android settings are `vulkan_sparse_shared_memory=false`, `present_sgsr=true` and `present_max_height=1080` (`lr_android_main.cpp:81-125`). Its ADPF thread picker skips the "Vulkan Pipeline"/"Vulkan Storage" threads (`:272`). Its SDK patch has the same process-wide condition variable for multi-object waits that our SDK patch 40 replaced with per-handle wakeups.
- **Upstream ReXGlue:** `ignore_thread_priorities` and `ignore_thread_affinities` both default true (`src/system/xthread.cpp:40,43`). The SCHED_FIFO path fails with EPERM on Android (`threading_posix.cpp:661,838`).
- **Known upstream bugs:** SDL's never-blocking Android `SDL_WaitEvent` is libsdl-org/SDL#16601, still open (milestone 3.4.22). Our `SDL_HINT_POLL_SENTINEL=0` is a local workaround. The presenter's unset `swapchain_format` (our SDK patch 38) is also in Xenia Canary and upstream ReXGlue v0.10.1, and is worth upstreaming.
- **Not found anywhere:** a fix for guest worker threads spin-waiting on each other. Our futex replacement for LR's effect-worker spin primitives (lr_hooks.cpp) is new. No repo uses Choreographer, Swappy or `setFrameRate`.


### GPU cost of Xenia's Vulkan backend on mobile (2026-11-08)
- **XeniOS** (github.com/xenios-jp/XeniOS, branch `preview`; iOS/macOS Xenia fork, BSD): `vulkan_direct_host_resolve` (resolve host render targets straight to shared memory; shaders `resolve_host_color.xesli` 73 KB and `resolve_host_depth.xesli` 22 KB, whose SPIR-V is generated at build time and not committed) and `vulkan_transfer_in_draw_pass` (default on: eligible ownership transfers are encoded inside the following guest pass, with LOAD_OP_DONT_CARE when they overwrite the whole target; integer-format color transfers are not eligible). Code in `src/xenia/gpu/vulkan/vulkan_render_target_cache.cc` (CanQueueDrawPassTransfers, PreflightPendingDrawPassTransfers, EncodePendingDrawPassTransfers, TryDirectHostResolveCopy).
- XeniOS's `vulkan_render_target_cache.cc/.h` (branch `preview`) are in `refs/xenios/` (fetched 2026-11-09, read-only): `CanQueueDrawPassTransfers` / `PreflightPendingDrawPassTransfers` / `EncodePendingDrawPassTransfers` fold ownership transfers into the following guest pass (needs transfer pipelines per guest render pass key; written for render pass objects, we use dynamic rendering + GPL).
- **xenia-edge** (github.com/has207/xenia-edge): commits aa2efea/e1ba795 "Resolve host render targets directly into shared memory" (~5% GPU usage); 7101021 binds shared memory persistently for texture loads and resolves.
- **Theft4** (github.com/KoreanSeats1/Theft4; GTA IV on ReXGlue, iOS/Android): backported XeniOS's direct resolve (correct, fewer dumps, no FPS gain) and transfer merging (opt-in, no result published); their main path became a GTA-IV-specific renderer. CHANGELOG.md and THEFT4_GPU_DIAGNOSTIC_2026-09-16.md.
- **X360-Mobile** (Ashnar2602/X360-Mobile---OFFICIAL, release notes only): same options (transfer in draw pass, direct host resolve, a Turnip sysmem/gmem switch).
- **lr-ffxiii-port** (refs/lr-ffxiii-port): no GPU-load changes; its Android template lists direct_host_resolve, dynamic rendering off and gamma_render_target_as_unorm16 as toggles without measurements.

### Lost Odyssey recomp GPU layer (refs/LostOdysseyRecomp/LostOdysseyRecomp/gpu, studied 2026-11-08)
- High-level renderer (UnleashedRecomp lineage) on plume, ~52k lines; no Xenia EDRAM tile model. Render targets keyed by (tile base, storage class, pitch, depth); colour stored as RGBA16F, depth D32S8. Shaders translated from Xenos microcode to HLSL (XenosRecomp-derived printing, gpu/shader/xenos_translator.cpp), DXC to SPIR-V, cached; pipelines prebuilt from recipes, VkPipelineCache persisted (driver_pipeline_cache.h).
- Resolves: kept as host images keyed by guest address + format (renderer.cpp ~1043-1078); texture fetches of that address use them directly (~8517-8565), no guest-memory round trip.
- Ownership transfers: renderer.cpp ~3035-3090 + edram_transfer.h; a source holding only a pending whole-target clear is turned into a CPU-computed clear of the destination (ConstantTransfer, edram_transfer.h ~163-195); full-cover transfers drop pending clears.
- Clears: pending_clear.h queue, replayed at the pass that binds the target, folded into loadOp=CLEAR by the plume patch; vkCmdClearAttachments disables LRZ on Turnip.
- Adreno 750 measurements in docs/notes (render-pass-merging-*.md): Turnip autotune = sysmem for all passes; forcing GMEM 1.4-2.6x slower; ~305-320 passes per frame before their deferred-clear work; GTAO 10.8 ms (off on Android); occlusion-query waits expensive.
